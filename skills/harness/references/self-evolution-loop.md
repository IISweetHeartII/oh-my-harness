# 증거 주도 자율 진화 루프 (옵트인)

피드백 주도 진화(`skills/evolve`)는 **사람이 말해야** 시작되고, 사람의 문장을 근거로 삼으며,
편집 후 회귀를 자동으로 막지 못한다. 검증기를 갖춘 하네스라면 이 루프를 **실행 증거 기반의
자율 루프**로 격상할 수 있다.

이 루프가 답하는 질문은 하나다: **추가한 에이전트가 실제로 품질을 올렸는가, 아니면
숫자만 늘었는가.** 하네스 팩토리의 고질적 약점은 역할을 27개 찍어낼 수는 있는데 그중 몇 개가
값을 냈는지 아무도 모른다는 것이다. 여기서 다루는 것이 그 계측이다.

## 자격 분류 — 아무 하네스에나 적용하지 마라

두 전제가 모두 충족돼야 자율 루프가 의미를 갖는다. 무리하게 적용하면 «가짜 정밀성» 이 된다.

1. **결정적·재현 가능한 검증 신호** — pass/fail 검증기, 수치 KPI, 스키마 적합성, 탐지기
   재실행 등 사람 판단 없이 반복 측정 가능한 outcome. 대개 이미 있는 QA·팩트체크·감사
   에이전트의 출력이 신호원이 된다.
2. **분할 가능한 반복 과제 집합** — held-in / held-out 으로 나눌 수 있는 task 모집단.
   매 실행이 1회성 bespoke 잡(예: "이 칼럼 한 편")이면 분할이 성립하지 않는다.

| 클래스 | 조건 | 적용 |
|---|---|---|
| **A** | 결정적 신호 O, 분할 가능 O | 전체 루프 적용 |
| **B** | 신호가 부분적으로만 결정적(구조·스키마는 기계 검증 가능, 품질은 주관) | 구조적 하위검사에만 게이트 적용. 주관 축은 golden-sample 폴백 |
| **C** | 신호가 주관적이거나 과제가 1회성 | 자율 루프 미적용. `skills/evolve` 의 피드백 주도만 사용 |

판정을 못 하겠으면 **C 로 둔다.** 잘못 적용한 게이트는 없는 게이트보다 나쁘다 —
숫자가 붙어 있어서 틀렸을 때 더 믿게 된다.

## 실패 시그니처 스키마 `(c, q, m)`

실패 트레이스를 군집화할 때 세 축을 **분리해서** 기록한다. 섞으면 편집 표면을 특정할 수 없다.

| 축 | 뜻 | 예 |
|---|---|---|
| `c` — cause | 검증기가 «무엇을» 거부했나 | 스키마 필드 누락 / 사실 오류 / 형식 위반 |
| `q` — qualifier | «어떤 행동» 이 그 원인인가 | 이전 단계 출력을 검증 없이 재사용 / 근거 없이 추론 확장 |
| `m` — surface | «어디를» 고쳐야 하나 | 시스템 프롬프트 · 검증 지시 · 실패복구 지시 · 런타임 정책 · 에이전트 정의 · 스킬 |

핵심은 `c` 와 `q` 의 분리다. "스키마 필드가 비었다"(c)는 증상이고, "앞 단계 산출물을
그대로 믿었다"(q)가 원인이다. `c` 만 보고 고치면 같은 실패가 다른 필드에서 재발한다.

## 3단계 루프

### 1. 약점 채굴

현재 하네스를 held-in 과제에 실행해 트레이스를 모으고, **실패** 트레이스를 `(c, q, m)`
시그니처로 군집화한다.

이 단계는 **편집을 처방하지 않는다.** 증거 번들만 만든다. 채굴하면서 고치기 시작하면
관측과 개입이 섞여 무엇이 효과였는지 알 수 없게 된다.

### 2. 바운디드 제안

같은 모델·팀이 제안자로 돌아, 군집당 **서로 다른 · 최소 단위** 후보 편집 K개를 만든다.

- 각 편집은 **1 실패 메커니즘 ↔ 1 편집 표면**에 결박한다
- "전반적으로 프롬프트를 개선" 같은 편집은 반려한다 — 어느 부분이 효과였는지 측정 불가
- K는 3~5. 더 늘리면 게이트 통과가 우연이 될 확률이 올라간다

### 3. 검증 게이트

각 후보를 held-in **및 held-out** 양쪽에 재평가하고, 보수적 비퇴행 규칙으로만 채택한다.

```
Δ_in ≥ 0  AND  Δ_ho ≥ 0  AND  max(Δ_in, Δ_ho) > 0
```

held-out 은 제안자가 보지 못한 회귀 테스트다. 이게 없으면 관측된 실패에 과적합한 편집이
그대로 들어온다. **통과분만 병합한다.** 동률(둘 다 0)은 채택하지 않는다 — 이득 없는 변경은
표면적만 늘린다.

## 되돌리기·로깅 (필수)

- 편집 **전** 대상(에이전트/스킬/오케스트레이터)의 스냅샷을 보존한다
- 모든 전이를 기록한다: 편집 표면 · 양쪽 split 점수 · accept/reject · 사유
- 기록 위치는 CLAUDE.md 변경 이력. 채택이 헛발질이면 스냅샷으로 즉시 롤백한다

로깅이 없으면 이 루프는 그냥 «모델이 자기 프롬프트를 마음대로 고치는 것» 이다.
되돌릴 수 있어야 자율이 안전해진다.

## B·C 클래스 폴백 — 게이트를 강등하되 규율은 유지한다

결정적 검증기가 없다고 해서 규율까지 버리지 않는다.

- **유지**: 채굴 → 바운디드 제안 → 되돌리기 → 로깅
- **강등**: 게이트를 «기존 QA/리뷰 에이전트 판정 + 고정 golden-sample(과거 우수작 5~10개)에
  대한 LLM-judge 또는 사용자 승인» 으로 바꾼다

논문의 «사람 없는 자율» 은 포기하지만, **증거 기반 · 최소 · 표면 결박 · 되돌리기 가능**이라는
드리프트 방지 속성은 보존된다.

## 실행 모드별 오케스트레이션

| 모드 | 배치 |
|---|---|
| 워크플로우 오케스트레이션 | 가장 잘 맞는다. `pipeline(과제, 실행, 채점)` 으로 held-in/held-out 을 돌리고, 채점은 `schema` 로 강제해 숫자를 구조화한다 |
| 퍼시스턴트 에이전트 협업 | 제안자와 채점자를 **다른 에이전트**로 둔다. 같은 에이전트가 제안하고 채점하면 게이트가 무의미하다 |
| 서브에이전트 위임 | 채점 단계에만 쓴다. 채점자는 제안 맥락을 몰라야 한다 |

## 실패 모드 가드

- **제안자 = 채점자** → 게이트가 통과 도장으로 전락. 반드시 분리한다
- **held-out 이 held-in 에서 샘플링됨** → 회귀를 못 잡는다. 분할은 루프 시작 전에 고정한다
- **과제 수가 적음** → n<10 이면 Δ 가 잡음이다. 이 경우 C 클래스로 취급한다
- **채택 누적** → 매 라운드 최대 1~2건만 병합한다. 여러 편집을 한 번에 넣으면 기여를 못 가른다
- **스냅샷 없이 편집** → 롤백 경로가 없으면 루프를 돌리지 마라
